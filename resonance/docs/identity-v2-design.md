# Identity Service v2 — Design Doc

Status: **design only, not yet implemented**. Written 2026-09-12, before any code for this expansion exists. This is the full design for the identity-service overhaul requested to back avatars, profiles, email management, Google OAuth, MFA, and session management. Not saved as a throwaway chat artifact deliberately — Feature 2's original UX proposal got lost that way once already (see PROGRESS.md), not repeating that mistake here.

## 0. Scope

Six areas, in the order they'll actually get built (see §7 for why this order):

1. Profile fields (DisplayName edit, preferences)
2. Avatars (upload, resize, S3 storage, delete)
3. Session management (refresh tokens, rotation, revocation, multi-device session list)
4. Email change with double opt-in verification
5. Google OAuth (Sign in with Google, auto-provision or link-by-email)
6. MFA — TOTP (authenticator apps) + email OTP

## 1. External dependencies

| Dependency | Used for | Status |
|---|---|---|
| AWS S3 | Avatar storage | Needs bucket name/region + IAM Access Key ID/Secret from the user, scoped to `s3:PutObject`/`GetObject`/`DeleteObject` on one bucket |
| Resend | Email verification links, email OTP codes | Needs an API key (sandbox mode is enough to start) |
| Google OAuth 2.0 | Social login | Needs a Client ID/Secret from Google Cloud Console; redirect URI `http://localhost:5076/api/auth/google/callback` for local dev, a second one once ngrok deployment happens |

All three are **new external dependencies** for a project that's stayed free/local/self-hosted everywhere else (Python for Topics instead of a paid API, local Qwen2.5-3B instead of OpenAI). Not a problem, just worth being deliberate about — these are real accounts with real credentials that need to exist before the corresponding code paths function, and they introduce new secrets that must never land in git (see §6).

## 2. Domain model

All entities follow the existing convention: flat POCO, private setters, private parameterless ctor for EF, public validating ctor, no shared base class, `Guid.NewGuid()` generated by the caller (handler), not by the entity itself.

### 2.1 `User` (existing entity, extended)

Current shape: `Id, Email, PasswordHash, DisplayName, CreatedAt`.

Additions:
```
AvatarUrl          string?      // full S3 object URL, null until an avatar is uploaded
PreferencesJson     string?      // free-form JSON blob for lightweight prefs (see 2.1.1)
PasswordHashAlgorithm  enum { BCrypt, Argon2id }   // see §6.1 for why this exists
```

**2.1.1 What "preferences" means concretely** — this was vague in the original ask, so scoping it now rather than leaving it open: a single JSON blob (`PreferencesJson`, `Dictionary<string, object>` serialized) rather than individual typed columns, since preferences tend to accumulate and change shape over a project's life and a schema migration per new preference is friction nobody wants. Starting set (implemented as the profile settings UI ships, not all at once): theme (if dark/light ever becomes user-choosable instead of system-only), whether to receive email notifications for new chat messages (ties into the connections feature), default map view. Exposed via a typed C# DTO on the API boundary (`UserPreferencesDto`) even though storage is a blob — validation happens at the DTO layer, not the JSON.

### 2.2 `RefreshToken` (new)

```
Id              Guid
UserId          Guid
TokenHash       string      // SHA-256 of the actual token value — the raw token is never stored
DeviceLabel     string?     // parsed from User-Agent at issuance time, e.g. "Chrome on Windows"
IpAddress       string?
CreatedAt       DateTime
ExpiresAt       DateTime
RevokedAt       DateTime?
ReplacedByTokenId  Guid?    // set when rotated, points to the token that superseded this one
```

This is the "session" the account settings page shows and lets you terminate. A row with `RevokedAt == null && ExpiresAt > now` is an active session.

### 2.3 `ExternalLogin` (new — Google OAuth)

```
Id              Guid
UserId          Guid
Provider        enum { Google }   // only Google for now, but modeled as extensible
ProviderUserId  string            // Google's `sub` claim — stable, unlike email
Email           string            // Google's email at time of link, for display only
LinkedAt        DateTime
```

Lookup key is `(Provider, ProviderUserId)`, not email — emails can change on Google's side; `sub` doesn't.

### 2.4 `EmailChangeRequest` (new)

```
Id              Guid
UserId          Guid
NewEmail        string
OldEmailTokenHash  string
NewEmailTokenHash  string
OldEmailConfirmedAt  DateTime?
NewEmailConfirmedAt  DateTime?
ExpiresAt       DateTime      // both confirmations must land before this or the request is dead
CreatedAt       DateTime
```

The email only actually changes once **both** `OldEmailConfirmedAt` and `NewEmailConfirmedAt` are set — this is the "sent to both old and new addresses" requirement. Old-address confirmation proves the current account owner initiated it (not an attacker who's already compromised the new-email inbox); new-address confirmation proves they actually control the destination.

### 2.5 `TotpCredential` (new — authenticator app MFA)

```
Id                  Guid
UserId              Guid      // one per user; enrolling again replaces it
SecretKeyEncrypted  byte[]    // encrypted at rest, see §6.2
IsEnabled           bool      // false until the user confirms one correct code post-enrollment
CreatedAt           DateTime
```

### 2.6 `EmailOtpChallenge` (new — email-based OTP)

```
Id              Guid
UserId          Guid
CodeHash        string        // SHA-256 of the 6-digit code
Purpose         enum { Login, EmailChangeSensitive }
ExpiresAt       DateTime      // short-lived, ~10 minutes
ConsumedAt      DateTime?
CreatedAt       DateTime
```

### 2.7 `MfaChallenge` (new — bridges "password verified" and "fully logged in")

```
Id              Guid
UserId          Guid
ExpiresAt       DateTime      // ~5 minutes
CreatedAt       DateTime
```

Returned to the client after a correct password when the user has MFA enabled, instead of real tokens. The client then submits a TOTP or email-OTP code against this challenge ID. Prevents a password-correct-but-no-second-factor response from ever looking like a successful login.

## 3. API surface

All new endpoints live in `Resonance.Identity.Api/Program.cs` following the existing Minimal API + MediatR-dispatch pattern (no Controllers). Grouped by area:

**Profile**
| Method | Route | Auth | Purpose |
|---|---|---|---|
| GET | `/api/identity/me` | required | Current user's full profile |
| PATCH | `/api/identity/me` | required | Update `DisplayName`, `Preferences` |
| PUT | `/api/identity/me/avatar` | required | Upload/replace avatar (multipart form) |
| DELETE | `/api/identity/me/avatar` | required | Remove avatar |
| GET | `/api/identity/users` | required | Existing bulk lookup by ids (already designed) |

**Email change**
| POST | `/api/identity/me/email` | required | Start a change — sends both confirmation emails |
| GET | `/api/identity/email-change/confirm?token=` | none | Confirms one side (old or new); public link-click endpoint |

**Google OAuth**
| GET | `/api/auth/google/start` | none | Redirects to Google's consent screen |
| GET | `/api/auth/google/callback` | none | Google redirects here with an auth code; exchanges it, logs in or auto-provisions |

**MFA**
| POST | `/api/identity/mfa/totp/enroll` | required | Generates a secret + QR code payload |
| POST | `/api/identity/mfa/totp/confirm` | required | Confirms enrollment with one valid code, sets `IsEnabled = true` |
| DELETE | `/api/identity/mfa/totp` | required | Disable TOTP |
| POST | `/api/auth/mfa/challenge` | none | Given an `MfaChallenge` id + code (TOTP or emailed OTP), returns real tokens |
| POST | `/api/auth/mfa/email-otp/request` | none | Sends a fresh email OTP for a given challenge |

**Sessions**
| GET | `/api/identity/sessions` | required | List this user's active `RefreshToken` rows |
| DELETE | `/api/identity/sessions/{id}` | required | Revoke one session |
| DELETE | `/api/identity/sessions` | required | Revoke all *other* sessions (keep the current one) |
| POST | `/api/auth/refresh` | none (token in body) | Exchange a refresh token for a new access+refresh pair |

**Auth (existing, modified)**
- `POST /api/auth/login` — now returns *either* `AuthResponseDto` (unchanged shape, MFA disabled) *or* `{ mfaChallengeId, availableMethods: ["Totp","EmailOtp"] }` (MFA enabled). Also now issues a `RefreshToken` alongside the access token, and access token lifetime shrinks from 1440 to 15 minutes (see intro).
- `POST /api/auth/register` — unchanged shape, but password hashing now goes through the versioned algorithm (§6.1).

## 4. Flows

**Register/login, MFA disabled** — unchanged from today, plus a refresh token now issued alongside the access token.

**Login, MFA enabled**: password verified → `MfaChallenge` created → client shown a code-entry screen → client posts code to `/api/auth/mfa/challenge` → server validates against `TotpCredential` or `EmailOtpChallenge` → real tokens issued, challenge consumed.

**Avatar upload**: client posts multipart image to `/api/identity/me/avatar` → server validates content-type/size (cap ~5MB, restrict to jpeg/png/webp) → resizes to a fixed set of variants (e.g. 256px, 64px) using `SixLabors.ImageSharp` (pure managed, no native binary dependency, free for this project's scale under Six Labors' license terms) → uploads resized bytes to S3 under `avatars/{userId}/{variant}.webp` → old object deleted if one existed → `AvatarUrl` updated. Server-side resize (not client-side, not direct-to-S3 presigned upload) chosen deliberately: keeps file-type/size validation server-side rather than trusting the client, and avoids a second architecture (presigned URLs) for a diploma-project-scale feature. Worth revisiting if upload volume ever makes proxying through the API a bottleneck.

**Email change**: user submits new email → `EmailChangeRequest` created, two tokens generated → Resend sends "confirm this change" to the *old* address and "confirm this is your email" to the *new* address → each link hits `/api/identity/email-change/confirm?token=` → once both are confirmed, `User.Email` updates and the request record is done. Expires (e.g. 24h) if not both confirmed.

**Google sign-in, new user**: client hits `/api/auth/google/start` → redirect to Google consent → Google redirects to `/callback` with a code → server exchanges code for tokens via Google's token endpoint → validates ID token → extracts `sub` + `email` → no `ExternalLogin` row for that `sub` → check for an existing `User` with that email → none found → auto-provision a new `User` (no usable password — `PasswordHash` set to a sentinel that can never match any BCrypt/Argon2 comparison, so password login stays impossible until they explicitly set one) → create `ExternalLogin` link → issue tokens.

**Google sign-in, linking**: same as above but a `User` with that email *does* already exist → link the new `ExternalLogin` to that existing user instead of creating a new account → issue tokens for the existing account. (Worth a product decision later: should this require the existing account to confirm via a logged-in session first, to prevent someone claiming an email they don't control? Google having verified the email address already covers most of this risk, but flagging it as a known simplification.)

**Refresh token rotation**: client posts its refresh token to `/api/auth/refresh` → server hashes it, looks up the `RefreshToken` row → if revoked *and* it's being reused, treat as theft: revoke the entire token family (walk `ReplacedByTokenId` backwards, or simpler — revoke all of that user's tokens) → if valid, revoke this row (`RevokedAt = now`), issue a new access+refresh pair, set `ReplacedByTokenId` on the old row to the new one.

## 5. Security decisions worth flagging explicitly

**6.1 — Password hashing: keep BCrypt for existing users, offer Argon2id for new ones.** The prompt said "BCrypt or Argon2" as if picking one; the real-world answer for an *existing* system with real password hashes already in the DB is neither purely — you can't retroactively re-hash a password you don't have in plaintext. Add `PasswordHashAlgorithm` on `User` (defaults `BCrypt` for existing rows via migration), verify against whichever algorithm the row says, and hash *new* passwords (registration, password changes) with Argon2id going forward. This is the standard "algorithm migration" pattern — don't force a breaking change on every existing account to satisfy a spec word choice.

**6.2 — TOTP secret encryption.** `TotpCredential.SecretKeyEncrypted` needs actual encryption at rest (not just "it's in a normal column"), since anyone with DB read access could otherwise generate valid codes for any user. Use ASP.NET Core's `IDataProtector` (built-in, no new dependency) keyed per-purpose (`"TotpSecret"`), not a hand-rolled AES implementation.

**6.3 — Refresh tokens stored hashed, never raw.** Same reasoning as password hashes — DB compromise shouldn't hand over usable session tokens. `TokenHash` is a SHA-256 of the actual token (a refresh token isn't a password a human needs to be slow-hashed against brute force the way BCrypt/Argon2 protect against — SHA-256 is appropriate here specifically because the token itself is already high-entropy random data, not something guessable).

**6.4 — Access token lifetime must shrink.** Currently 1440 minutes (24h) with zero revocation. Once refresh tokens exist, keeping access tokens long-lived defeats the entire point of "view/terminate sessions" — a terminated session's *access* token would still work for up to 24 more hours. Drop to 15 minutes; the refresh flow makes short-lived access tokens invisible to the user.

**6.5 — Secrets management.** AWS keys, Resend API key, Google Client Secret, and the `IDataProtector` key ring all need to stay out of git. This project currently puts JWT secrets directly in `appsettings.Development.json` (committed) — acceptable for a shared dev-only HMAC secret that's the same across all services by design, but AWS/Resend/Google credentials are a different category (real external accounts, potentially billable, tied to a person). These should go in user-secrets (`dotnet user-secrets`) or environment variables passed via docker-compose, **not** committed `appsettings.Development.json`, even in this project's otherwise-relaxed convention. Worth a deliberate exception, not an oversight.

## 7. Implementation order

1. **Profile fields + sessions** — no external deps, can start immediately once this doc's approved.
2. **Avatars** — needs AWS credentials (§6.1).
3. **Email change** — needs Resend key (§6.2).
4. **Google OAuth** — needs Google credentials (§6.3), independent of email/avatars so can happen in parallel with either.
5. **MFA (TOTP first, then email OTP)** — TOTP has no external dependency and can move up if you want it sooner; email OTP is blocked on Resend same as email change.
